# 技术选型尽调 · 前端框架深度对比（稳定性/健壮性/可维护性）

> 生成于 2026-10-13 · 证据来源：GitHub API 仓库与 Release 数据（检索于当日）、官方文档、社区生产环境经验（Reddit/GitHub Issues/技术博客）
> 服务对象：PRD v0.2 的五类页面（仪表盘/画像库/领域探索/组合评估/穿透分析），Windows 主机，单维护者（量化新手 + AI 结对），预期生命周期 ≥3 年

## 0. 评估基准：这个项目里三个词的具体含义

- **稳定性**：框架本身的存续风险（出品方、版本阶段、发布节奏）+ 升级时破坏性变更的频率。
- **健壮性**：akshare 接口失败/超时时应用的表现——卡不卡、错在哪、怎么恢复。我们的数据源是爬虫型免费接口，失败是常态而非异常，这一维度权重最高。
- **可维护性**：单人 + AI 结对三年后的代码还改不动的风险——状态管理机制、测试能力、重构友好度、AI 修复该框架 bug 的语料充足度。

## 2. 逐框架深评

### 2.1 Streamlit

**执行模型**：每次交互（勾选基金、拖滑条）从上到下**重新执行整个页面脚本**。这是它一切优缺点的根源。

代码层面的后果：
1. 昂贵操作必须 `@st.cache_data` 包裹，否则每次勾选都重拉 akshare（卡顿 + 被数据源限流）。缓存 TTL 成为正确性的一部分——忘记设 TTL，你看到的永远是旧数据且不自知。
2. 跨组件状态只能走 `st.session_state`——本质是字符串键的字典，无类型检查；重命名一个 key 靠全局文本搜索；官方 issue #4828（按钮重复点击跳过逻辑）是这类坑的典型样本。
3. 页面脚本天然过程式：逻辑与渲染交织，单页超过 ~300 行后维护性明显下滑（社区大量「如何组织 Streamlit 代码」文章的存在本身就是普遍痛点的证据）。
4. 缓解项：`st.fragment` 局部重跑解决性能问题；官方 `AppTest` 测试框架（st.testing.v1）可对整页做冒烟测试——测试能力从无到有。

**健壮性**：akshare 阻塞调用期间整页挂起（可加 spinner 但不能并行操作其他控件）；未捕获异常直接在页面抛大红栈。标准防御是 try/except + `st.error` + 显式 TTL 缓存——全靠写代码的纪律。WebSocket 断线重连经过百万级应用验证，网络抖动恢复成熟。

**稳定性**：Snowflake 养核心团队；1.x 语义化版本以来 API 稳定（月更都是加法）；按规模归一化后 issue 比例健康。3 年存续风险：低。

**可维护性**：小规模（我们的 5 页、数据毫秒级）时代码量最少、最直白；AI 结对修复能力**全场最强**（训练语料最多，你踩的坑几乎都有人踩过并写过）。规模上去后受 session_state 与过程式脚本拖累，上限低。

**硬伤**：跨页联动逻辑（如"领域探索页的筛选要影响穿透页默认值"）会写出绕弯代码；深定制 UI 做不到。

### 2.2 NiceGUI

**执行模型**：真事件驱动 + async。每个 `@ui.page` 是每客户端独立的状态树，按钮 `on_click` 是回调而非重跑整页——**状态就是普通 Python 对象，根本不存在 session_state 这类间接层**。这是 Reddit 社区把它列为「状态管理更好的 Streamlit 替代」第一名的根本原因。

代码层面的后果：
1. 心智模型接近传统桌面 GUI / 后端服务，OOP 组件化干净，IDE 重构（改名/提取方法）真正可用。
2. 所有 handler 是 async，而 **akshare 是同步阻塞库**——直接调用会冻结事件循环（该客户端甚至其他客户端的页面全部卡死）。必须 `run.io_bound`（即 asyncio.to_thread）包一层。GitHub issue #4891 表明与 multiprocessing 混用的边缘场景仍可能挂。这是健壮性上真实的坑，需要一条团队纪律：**一切外部 IO 走 io_bound**。
3. 没有官方 AppTest 等价物，UI 测试基建要自己搭（pytest + httpx + 元素选择器）。

**健壮性**：底座是 FastAPI/Starlette + Vue/Quasar——生产级 ASGI 服务器语义直接继承，错误处理是标准异常路由那一套。async 纪律遵守时，故障隔离好于 Streamlit；违反时（忘了 io_bound），卡死是全页面级别的。

**稳定性**：zauberzeug 自家产品在用（自用驱动开发）；65 个 open issues（绝对数与比例都健康）；月更节奏；3.x 阶段，历史主版本升级（1→2→3）各有迁移文档，节奏慢、可预期。

**可维护性**：单语言 Python；类型与重构友好度中上；AI 结对语料中等（远少于 Streamlit，多于 Reflex）。长期上限高于 Streamlit。

**硬伤**：生态位小——想换社区组件时选择少；异步编程对量化新手是新概念（AI 可兜底但你要能看懂）。

### 2.3 FastAPI + React（AntD + ECharts）

**执行模型**：彻底分层。后端纯 API（pydantic 定义每个响应 schema），前端组件树（hooks 管状态，React Query/SWR 管数据获取、缓存与自动重试）。

代码层面的后果：
1. 三者中唯一能做到**业务逻辑零 UI 依赖**：组合评估、穿透计算是纯函数，100% 常规 pytest 单测，不用起任何 UI。测试故事最好。
2. akshare 失败只污染一个 endpoint，返回结构化错误 JSON，前端 toast + React Query 自动重试——**健壮性天花板最高**，故障隔离最干净。
3. 类型从 SQLite → pydantic → TS interface 一路贯穿，改字段名编译器当场报错——重构安全性最高。
4. 代价：维护面翻倍（Python 依赖 + node_modules 两套工具链、两份锁文件）；React 状态管理需要架构纪律，初学者容易写出一坨 useEffect；学习成本数周级（React + TS + 构建链），与每周 6-10 小时预算冲突最狠。

**稳定性**：FastAPI 与 React 都是各自生态最头部项目（React 由 Meta 维护十年），AntD/ECharts 为蚂蚁/Apache 顶级——十年期存续风险全场最低。

**可维护性**：上限最高（模块化、双端类型、组件复用、测试全谱）；**下限也最低**（架构纪律要求最高，没人管你的时候最容易烂）。AI 结对双半边语料都海量，但你需要能读懂 AI 生成的代码才能验收——这个门槛绕不过去。

### 2.4 Reflex（从 demo 候选移除，理由存档）

28,947 星但 2022 年 10 月才出生，**当前 0.10——pre-1.0**。官方 changelog 明示破坏性变更常态化：弃 Python 3.10、0.8→0.9 需专门迁移指南（db_url 显式化、setter API 变更、部署调整）、0.8 内部大重构（Pydantic 替换 + Vite/Rolldown）。对一个「写完放 Windows 主机跑三年不再折腾」的目标，版本高速漂移是稳定性维度的实质减分。降级为观察名单，1.0 后再评。

## 3. 维度对比总表

| 维度 | Streamlit | NiceGUI | FastAPI+React |
|---|---|---|---|
| 稳定性（存续/版本） | A（Snowflake、1.x 稳定期） | A-（公司自用、3.x、Starlette 底座） | A+（双生态头部） |
| 健壮性（akshare 失败场景） | B（整页挂起待恢复；靠纪律防缓存陷阱） | B+（事件循环隔离好，但 io_bound 纪律是硬前提，违反即全卡） | A（endpoint 隔离 + 自动重试 + 类型校验） |
| 可维护性（我们的规模下） | B+（代码最少；session_state 与过程式是天花板） | B+/A-（OOP 干净；测试自搭；AI 语料中） | A 上限 / C 起步（纪律决定一切） |
| 学习成本 | 周末级 | 一周级（async） | 数周级 |
| AI 结对修复力 | 最强 | 中 | 强 |
| 对 5 页小工具的适配 | 舒适区 | 舒适区 | 略重但为长期上限买单 |

## 4. 结论

demo 候选维持三席：**Streamlit+Plotly、NiceGUI+ECharts、FastAPI+React+AntD+ECharts**；Reflex 移除（pre-1.0）。demo 增加一个专门的健壮性演示环节：内置一个「会延迟 3 秒且随机失败」的假数据源，让你在三个 demo 里亲手触发失败，体验卡不卡、报错样式、恢复过程——把抽象的健壮性差异变成可感知的对比。
